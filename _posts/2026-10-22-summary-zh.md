### [LiteLLM 1.107.0 遭供应链攻击，被指植入凭据窃取器与后门](https://safedep.io/litellm-pypi-compromise-credential-stealer-backdoor/) ⭐️ 8.0/10

据 SafeDep 的分析，PyPI 上的 LiteLLM 1.107.0 版本遭供应链攻击，安装后会植入凭据窃取器和后门。受影响的是在 AI/LLM 工具链中依赖该包的项目和开发者。目前可得的摘要未提及受感染安装量、恶意版本在 PyPI 上存留时长或修复版本，细节仍需以原报告核验。

hackernews · abhisek · 10月21日 14:00 · [社区讨论](https://news.ycombinator.com/item?id=50181114)

**「背景」** LiteLLM 是一个 Python 库兼模型网关，用统一的 OpenAI 兼容接口对接多家模型供应商，因此常被放在应用与各家 API 之间的请求路径上，进程里往往同时握有多个供应商的密钥。这也解释了为何该包被植入窃密程序后，攻击者能直接从运行环境中收集凭据；据安全厂商披露，1.107.0 的七个 wheel 文件（覆盖 Linux、macOS、Windows）都把恶意文件装进 site-packages，且在任何 Python 进程启动时即执行，无需显式 import litellm。评论者还提到今年 3 月曾发生过一次 LiteLLM 的 PyPI 供应链攻击，若属实，这已是约一年内的第二次。

**「对使用者的影响」** 任何在受影响环境中安装过 LiteLLM 1.107.0 的团队都应假设凭据已泄露：恶意代码随所有七个 wheel 写入 site-packages，并在主机上任意 Python 进程启动时执行，即使该进程从未导入 litellm。因此处置不能只停留在卸载或降级包，还需检查通过 PyPI wheel 和 Docker 镜像部署的主机、轮换相关密钥，并将依赖锁定到 1.107.0 之前的版本；LiteLLM 已移除公共注册表中指向其 GitHub 组织的受信任链接，以防再次发布恶意包。

**「社区讨论」** 有评论者称这已是 LiteLLM 近一两年内第二次重大供应链攻击，并引用报道称攻击者攻破了三名开发者的 GitHub 凭据，认为问题具有系统性，建议把 LiteLLM 固定在 1.107.0 之前的版本。另有评论指出，沙箱和权限规则难以防住这类攻击，权限弹窗疲劳和对 brew、npm 等安装流程的习惯性信任会削弱开发者的防线。

### [DuckDB 2.0.0 LTS 发布：新增客户端-服务器模式与触发器](https://duckdb.org/2026/10/21/announcing-duckdb-200) ⭐️ 8.0/10

DuckDB 发布 2.0.0 LTS 版本，代号「Cinnamon Teal」，新增客户端-服务器（client-server）部署能力和触发器（Triggers），并宣称改进了多核并行扩展性能。该版本面向需要在集中式服务中运行分析查询、或依赖事件触发逻辑的数据与软件工程师。需要注意的是，目前只有发布公告，没有提供基准测试或技术细节；关于高核数机器上性能提升的说法来自社区用户的实际使用经验，而非厂商提供的独立测量结果。

hackernews · nnx · 10月21日 14:01 · [社区讨论](https://news.ycombinator.com/item?id=50181136)

**「背景」** DuckDB 最初以嵌入式列式 OLAP 数据库为定位，通常作为进程内组件直接嵌入应用，而不是采用独立的服务器架构。正因如此，2.0.0 LTS 引入客户端-服务器能力才构成明显的架构变化；官方安装页也将 LTS 版本与不适合生产使用的开发预览版区分开来。

**「高核实例选型需重新评估」** 对在高核云主机上运行分析负载的团队，社区用户报告 DuckDB 2.0 把接近 100% CPU 利用率的上限从约 64 vCPU 提升到 128–192 vCPU，且更高利用率能转化为更快的作业完成速度；这意味着原先按 64 核以内选型的实例规格值得重新测试，而超过约 192 vCPU 后加速基本消失，继续加大规格未必划算。需注意该数据来自用户自述的生产观察而非官方基准，官方公告仅确认这是 2.0.0 LTS 版本发布。

**「社区讨论」** 有用户报告称，在 EC2 高核数实例上，2.0 版本仅计算部分就明显更快，CPU 利用率在约 128 至 192 vCPU 范围内更易达到 100%，而 2.0 之前扩展性大约在 64 vCPU 处见顶，超过 192 vCPU 后仍难见加速；该用户称这使其得以扩展开源记录链接工具 Splink。另一名用户表示已在生产环境将 alpha 版用作小型组织的集中式分析服务器，并自行开发扩展以通过 Postgres 线协议或 Arrow Flight 接入，因为 DuckDB 自有 Quack 协议的客户端支持目前仍很有限；也有人认为客户端-服务器架构和触发器分别会让 DuckDB 替代部分现有数据栈、更接近“开箱即用的数据仓库”。这些均为个人经验与判断，尚未经过独立验证。

### [PHP 8.2.35 安全版本发布，关联严重 RCE 披露](https://github.com/php/php-src/releases/tag/php-8.2.35) ⭐️ 8.0/10

PHP 8.2.35 已作为安全版本发布，但发布标签本身没有列出具体修复的漏洞编号、影响范围或利用条件。相关讨论将该版本与一个严重 PHP RCE 的协调披露联系起来，评论称 Wiz、Calif 和 OpenAI 参与其中，并提到 php2shell 项目页面；这些说法尚未由发布说明证实。运行 PHP 8.2 的用户应查阅官方公告并评估升级；在公告明确前，8.2.35 与上述 RCE 的对应关系仍不完整。

hackernews · tuyuri · 10月21日 13:45 · [社区讨论](https://news.ycombinator.com/item?id=50180873)

**「背景」** PHP 8.2.35 是 PHP 8.2 分支的安全更新，与代号 PHP2Shell 的严重远程代码执行漏洞的协调修复有关。Wiz Research 表示，其于 2026 年 8 月 19 日发现首个漏洞，并与 PHP、OpenAI 和 Calif 共同推进修复；Sansec 的记录显示 PHP 已发布修复版本，并由上述各方联合披露。

**「影响与处置」** 外部报道称，10 月 21 日这批修复针对两个 CVSS v4.0 评分为 9.2 的远程代码执行漏洞，影响 PHP 5.4 及之后的所有版本；Sansec 表示已在 Magento 2.4.9 以及另外十个 PHP 应用上确认存在未认证的远程代码执行。因此，仍运行 8.2.x 的站点应把 8.2.35 当作需要尽快部署的安全补丁，而不只是常规维护更新。部署时还需留意发布节奏：有评论者指出，新标签出现后镜像并未同步就绪，自动构建流水线可能拉到空标签，因此应确认所用镜像或发行版已实际包含修复。

**「社区讨论」** spenvo 记录了发布后数小时容器镜像仍不可用的情况，认为这给部署带来困难，并因此质疑发布流程；basilgohar 则表示，自己 20 年 PHP 托管经历中从未因漏洞预防性下线服务器，同时批评此次处理方式。OscarCunningham 引用外部帖子称可能存在第二个漏洞，但该说法未获发布说明确认。

### [eMudhra 中间 CA 私钥可被穷举，浏览器紧急封禁](https://scotthelme.co.uk/eight-bits-of-trust-emudhras-ca-keys-cracked-in-milliseconds/) ⭐️ 8.0/10

安全报告称，印度证书机构 eMudhra 的 8 张中间 CA 私钥随机性极弱，只有 256 种可能，能被现有工具快速穷举还原；其中 6 张可签发网站 TLS 证书，2 张可签发代码签名证书。原报告者用 Google 的 paranoid\_crypto 检查 CCADB 现有证书后称，未再发现其他命中。社区转述的处置信息显示，Mozilla 在 10 月 17 日收到报告后 3 小时内向 Firefox 用户推送封锁，Google 同日屏蔽受影响公钥并计划在 10 月 27 日移除相关根证书，Apple 和 Microsoft 也在跟进。上述细节来自博文与社区转述，尚无独立验证；无法更新 CA 包的 IoT 设备被视为最难处理的部分。

hackernews · hkc · 10月21日 09:08 · [社区讨论](https://news.ycombinator.com/item?id=50177916)

**「事件背景」** 中间 CA 证书由根 CA 授权，用于签发终端证书；其私钥一旦可被还原，攻击者就能为网站伪造受信任的 HTTPS 证书。据 Mozilla 的事件时间线，研究人员 Wayne 于 2026 年 10 月 17 日发现 eMudhra 的密钥可被破解，并向浏览器根计划及 eMudhra 提交了私钥控制证明（tool-2-2）；eMudhra 随后吊销了 8 张受影响的中间证书（tool-2-3）。

**「实际影响」** 根据报告，攻击者一旦还原这 8 张中间证书的私钥，就能冒充 eMudhra 为任意域名签发看似合法的 HTTPS 证书，其中 2 张还可用于代码签名，因此除浏览器访问外，软件与更新的签名校验同样在风险范围内。对运维方而言，实际动作是尽快更新随附 CA bundle 的组件（操作系统 ca-certificates 包、certifi、Node、Homebrew）并重建容器镜像；无法升级固件的 IoT 设备会在信任库移除前持续信任这批证书，只能依靠网络侧拦截或更换设备来缓解。

**「社区讨论」** 评论区中，jlmorton 讽刺称拥有约 100 个受信任 CA 可能本就过多；jasonjayr 则指出，能更新的设备可按建议更新系统 CA 包、certifi、Node、Homebrew 和容器镜像，真正困难的是无法更新的 IoT 设备。另有评论者提出，能否反过来利用这些弱密钥为不可更新设备签发证书以越狱。
