rss · Semianalysis · Oct 19, 05:39

The release requires Python 3.11 or newer and is installable with \`uv pip install --prerelease=allow sglang==0.5.22\` or the \`lmsysorg/sglang:v0.5.22\` Docker images for NVIDIA CUDA 13, AMD MI35x/MI30x, Intel GPU and Intel CPU.

**「Upgrade considerations」** Because the minimum interpreter is now Python 3.11, deployments pinned to Python 3.10 or earlier must upgrade their runtime before adopting v0.5.22. ### [Wine ported to OpenBSD, with changes kept OpenBSD-specific](https://marc.info/?l=openbsd-ports&amp;m=179236125692175) ⭐️ 7.0/10

A port of Wine, the compatibility layer for running Windows binaries on Unix-like systems, has been produced for OpenBSD and announced in a message on the openbsd-ports mailing list. In a follow-up message quoted in the discussion, the porter says much of the work is unlikely to be merged upstream, because the OpenBSD-specific handling — %gs stubs that are unnecessary on Linux, and a working but less optimal SIGUSR1 path — is explicitly marked OpenBSD-only to keep the changes clearly delimited. The available material does not state which Wine version was ported, whether the port has been committed to the OpenBSD ports tree, or which Windows applications have been tested.

hackernews · iamnothere · Oct 19, 13:35 · [Discussion](https://news.ycombinator.com/item?id=50152307)

**「Background」** Wine is a compatibility layer that implements Windows APIs so Windows binaries can run on non-Windows systems. A central obstacle for OpenBSD is that the OS does not permit user-space code to set the GS base register, which Windows applications use to access thread-local storage. The port therefore had to account for that platform restriction rather than relying on the usual mechanism.

**「Impact」** OpenBSD users gain a potential route to running Windows software without a separate Linux compatibility layer, but they would depend on a locally carried patch set rather than upstream Wine support: since the porter deliberately scoped the changes as OpenBSD-only, subsequent Wine updates would require those patches to be reapplied and maintained by OpenBSD porters.

**「Community Discussion」** Several commenters responded with wordplay, noting that the porter&\#x27;s surname, Frohwein, translates as &quot;happy wine&quot; in German and that the port could have been named &quot;Port.&quot; One commenter offered the opinion that the news is especially welcome as OpenBSD is &quot;shaping up to be a refuge from slopcode.&quot;

Mistral has announced Timestral, a family of time-series foundation models, according to the company&\#x27;s announcement page. hackernews · groar · Oct 19, 09:59 · [Discussion](https://news.ycombinator.com/item?id=50150434)

**「Background」** Time-series foundation models are pretrained forecasters intended to work on unseen series without training a separate model for each one; Mistral&\#x27;s Timestral family offers zero-shot forecasting in 5M, 28M, 123M, and 209M parameter versions, with the 209M checkpoint published on Hugging Face. Mistral frames the target use cases as enterprise forecasting, from sensor telemetry and observability metrics to capacity planning, energy, supply chains, risk, and maintenance.

**「Practical impact」** Because Timestral 1.0 is offered in sizes from 5M to 209M parameters for zero-shot forecasting, teams can test it against existing series without training a separate model for each one, using past-only and known-future covariates with context up to 32K timesteps. Its 21-quantile probabilistic output also means downstream pipelines must be set up to consume forecast distributions rather than single point predictions. Mistral&\#x27;s reported first-place rankings on GIFT-Eval, TIME, and fev-bench are vendor claims, so a pilot on your own data remains advisable before replacing an existing forecaster.

**「Community discussion」** Commenters debated whether a single general-purpose forecaster makes sense: one questioned lumping all time series into one category and argued accuracy comes from joint information, while another countered that the real case is forecasting thousands of series that each have too little history for their own model, making one shared model with scale-mismatch handling the alternative. Others raised skepticism about zero-shot claims — asking whether large quant firms already have comparable internal systems — and one reported a disappointing prior experience with a different Mistral model on coding tasks, though without benchmarks for Timestral itself.

### [Let&\#x27;s Encrypt adds two remote perspectives to domain validation](https://community.letsencrypt.org/t/lets-encrypt-is-adding-two-additional-remote-perspectives-for-domain-validation/252166) ⭐️ 7.0/10

Let&\#x27;s Encrypt is adding two additional remote perspectives to its ACME domain validation, expanding the number of physical network locations from which challenge/response checks are performed. The change is intended to make network-level attacks on certificate issuance harder. The supplied material does not specify a rollout date, the total number of perspectives, or measured effectiveness.

hackernews · gslin · Oct 19, 10:53 · [Discussion](https://news.ycombinator.com/item?id=50150809)

**「Why multiple validation perspectives matter」** Multi-perspective domain validation checks an ACME challenge from several separate network locations, so a single hijacked route cannot satisfy the challenge alone. Let&\#x27;s Encrypt already used multiple remote perspectives; the new change raises issuance to seven validation requests—one primary and six remote—and is tied to the CA/Browser Forum&\#x27;s updated Baseline Requirement 3.2.2.9, which mandates multi-perspective issuance corroboration. The added perspectives are scheduled to take effect on December 15, 2026.

**「Limits remain」** The extra perspectives narrow the window for network-level attacks on ACME validation but do not close it: in the August 2026 Hetzner/Softaculous hijack, an attacker holding a forged, RPKI-invalid route still obtained a technically valid TLS certificate for the victim&\#x27;s domains and used it to serve a malicious update. Certificate subscribers therefore still depend on routing security \(RPKI filtering, prefix announcements\) rather than on multi-perspective validation alone.

**「Community discussion」** One commenter explained that &quot;remote perspectives&quot; means checking an ACME challenge from multiple physical locations and therefore multiple network routes, so that network-level attacks become more difficult. Another commenter cited an August route-hijack incident in which an attacker obtained a valid TLS certificate despite multi-perspective validation by hijacking a Hetzner-hosted network block; the commenter said the stolen route was RPKI-invalid but was still accepted by most of the internet.
